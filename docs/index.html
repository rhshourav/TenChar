Built to know as little as possible

Most messengers ask who you are first. TenChar asks for a code that two people share, and then gets out of the way.

No identity to give up

No accounts, phone numbers, names, analytics or Google services. You pair by typing a one-time code, and the code stops working once both of you have joined.

Keys that keep changing

A Double Ratchet built from the Signal specification gives every message its own key. Losing one key does not expose the past, and the conversation recovers from the future.

A relay that can’t read

A small mailbox carries sealed envelopes. It never sees plaintext or the code. Run your own on Cloudflare Workers or Node, and list several so one outage doesn’t stop you.

Every message looks alike

Short messages always fill one 135-byte envelope. Someone watching the wire can’t tell “ok” from “see you at 8”.

English and Bangla

Messages count what you see as characters, so conjuncts and emoji are one each. The interface speaks English and Bangla, on Android and on desktop.

Many chats, one device

Android keeps up to 20 separate pairings, each with its own room, keys and relays, with names and emoji avatars you choose. Nothing syncs to a server.

Pairing a stranger-proof way

The relay can’t swap your keys and you can check it yourselves, in four steps.

  1. Share a code

    One phone shows an 80-bit code. The other types it. Say it aloud or show it in person.

  2. Commit, then reveal

    Each phone locks in its keys with a hash first and reveals them only after both have. Nobody can tune their keys to the other’s.

  3. Compare a number

    Both screens show the same 8-digit number. If they differ, someone is in the middle: cancel.

  4. Talk

    The code is spent. Messages go through the ratchet, and either of you can send first.

What it protects, and what it can’t

A privacy tool earns trust by being plain about its limits.

Protects against

  • A relay or its operator reading or changing messages
  • Network attackers, with TLS and end-to-end encryption
  • Someone who finds the pairing code after pairing is done
  • Replayed, reordered, injected or reflected messages
  • Leaking message length, since every frame is the same size
  • Later compromise of a single message key

Does not protect against

  • Malware on an unlocked phone, or a keyboard that records you
  • Metadata: the relay and its host see IP addresses, timing and message counts
  • The other person keeping or screenshotting what you send
  • Denial of service or a relay going offline
  • Memory inspection: wiping secrets is best effort

No independent review yet. The handshake and ratchet are written from the specifications and checked against independent test vectors, but no outside cryptographer has reviewed them. That review is the one thing the project can’t supply for itself.

Where it’s going

The honest status of the work, including what isn’t built.

Planned

Talk with no internet

A mesh of nearby phones and computers over Wi-Fi and Bluetooth, so private messages still work when the network doesn’t. Same end-to-end encryption, no relay needed. This is a design goal today, not shipped code.

Needed

Independent cryptography review

An outside look at the handshake and ratchet, on both the Kotlin and C++ implementations.

Untested

Windows and macOS builds

The desktop client was built and tested on Linux. Windows build scripts and a macOS path exist but haven’t run on those systems yet.

Deciding

Stronger passphrase hashing, installers, signing

The desktop vault uses PBKDF2 and is considering Argon2id. Signed installers and reproducible builds haven’t started.
